# 孤立候选模型的归档与恢复

[English](adapter_archive_recovery.md) | [简体中文](adapter_archive_recovery.zh-CN.md)

2026-10-24：孤立候选采用“先归档、核验可恢复，再清理”的处理顺序。完整副本及文件校验清单是清理前提。

## 启动恢复

可写 Runtime 先恢复数据库中的作业状态，核验并加载已提交模型，再处理当前运行的 `adapters` 目录。仅识别本学习器生成的 `hf_` 加 32 位小写十六进制版本名。当前模型、在途任务引用和本进程已登记模型都受保护；未知命名目录保留并继续占用版本额度。只读评估不执行归档恢复。

每个孤立候选（包括保存中断产生的不完整候选）执行：

1. 检查路径位于该运行的模型目录内，拒绝链接、Windows 重解析点及不能完整读取的目录。
2. 复制到同一运行下的 `research_archive/orphan_adapters/.pending_<版本>_<唯一编号>/payload`，记录每个文件的字节数、SHA-256、空目录和原始路径。
3. 刷新文件、核对归档内容，再将归档目录更名为最终名称；再次核对副本及未变化的原件。
4. 只有核验通过才逐文件清理原候选。复制、空间或校验错误不启动清理；清理中途失败时，完整归档已存在。再次启动可归档剩余部分，不覆盖先前的完整副本。

该流程要求每个运行目录由单个 Runtime 进程独占；不是多进程写入协调协议，也不声称已验证断电后的文件系统持久性。恢复事件通过现有审计接口记录。

## 手动恢复

在项目目录、项目 Python 环境中运行：

```powershell
.\.venv-local\Scripts\python.exe -m scripts.restore_adapter_archive <ARCHIVE_DIRECTORY> <NEW_RESTORE_DIRECTORY>
```

将占位符分别替换为归档目录和尚不存在的恢复目录。恢复前后都核对完整文件清单与校验值；已有目标目录不会被覆盖。该命令只恢复文件，不改变数据库当前模型指针，不把未提交候选变成当前模型。需要继续使用历史模型时，仍须核对其来源、模型配置和提交状态。

## 资源与验证边界

归档不在活跃 `adapters` 目录内，不被 Agent、Consolidator、检索器或训练器回查；正常运行不自动读取归档。它是研究者的离线恢复资料，不是额外学习记忆。归档仍消耗真实磁盘空间，复制时还需额外空间；空间不足则保留原件并受原有版本上限限制。如果恢复文件重新参与运行，必须重新计入状态及模型版本预算。原有正常模型退役按引用回收逻辑不变。

当前盘点中，带状态数据库的历史运行均没有孤立候选；无数据库的独立训练诊断产物保留。未对历史运行执行批量清理。

新增 11 项回归覆盖：容量释放及逐字节恢复、当前／退役／已登记模型保护、未知目录保留、复制失败、校验失败、源文件变化、不可读目录、清理中断和重试、拒绝覆盖、路径逃逸及链接拒绝、只读评估不归档。项目环境完整回归 **104 项通过**，日志位于 `tmp/archive-full-tests.log`。这些是文件与恢复流程测试，没有新增模型学习效果结论。

后续交付补充：远端仍登记的未知版本会保留，供部署负责人核对；不会因本地进程未登记就自动远端卸载。最新验证计数见[集群交接说明](cluster_handoff.zh-CN.md)。
